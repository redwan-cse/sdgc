# Local development with Docker Supabase

## Prerequisites

- Node **24.19.0** (Node 24.x supported) and npm **11.x**.
- Docker Desktop running with Linux containers and enough resources for Supabase.
- Git; optional GitHub CLI for repository operations.

The Supabase CLI is pinned in `devDependencies`; use `npx supabase` or the npm scripts. Do not install an unrelated global CLI. The configuration was generated by `supabase init` version 2.121.0, then deliberately adjusted.

## Install and start the frontend

```sh
npm ci
npm run dev
```

Frontend: <http://127.0.0.1:3000>. The foundation page requires no database keys. Fonts are packaged locally, so builds do not require Google Fonts access.

## Start this project's database services

From the repository root, check Docker and project status:

```sh
docker info
npx supabase --version
npm run db:status
npm run db:start
```

The first start downloads versioned container images and can take several minutes. The project ID is **sdgc**. There was an unrelated **sb-scratch** stack using ports 44321/44324 during initialization; leave it alone. Do not use `supabase stop --all`, `docker system prune`, or commands that remove another project's volumes.

| Service                   | Local address            |
| ------------------------- | ------------------------ |
| API / Auth / Storage      | <http://127.0.0.1:54321> |
| Postgres                  | `127.0.0.1:54322`        |
| Studio                    | <http://127.0.0.1:54323> |
| Local email capture       | <http://127.0.0.1:54324> |
| Shadow DB for schema diff | port `54320`             |

Prefer `127.0.0.1` consistently in the browser, env and auth redirects. The web app binds to loopback. Use the local stack only on a trusted development machine; follow the [Supabase local networking instructions](https://supabase.com/docs/guides/local-development) if working on an untrusted network. For port conflicts, change this repo's config/env/redirects together instead of stopping someone else's stack.

## Environment configuration

Recommended: after the local stack starts, run `npm run db:env`. It creates an ignored `.env.local` from this project's local status without printing credentials. It rejects non-loopback endpoints and preserves any existing `.env.local`.

For manual configuration, copy the example file using your shell:

```powershell
Copy-Item .env.example .env.local
```

On POSIX shells use `cp .env.example .env.local`. Run `npm run db:status` locally and place the local URL and publishable key in `.env.local`. The local legacy anon key can be used in `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` when the CLI exposes only that key. The secret/service-role key is only for tightly scoped server/test setup and must never receive a `NEXT_PUBLIC_` prefix.

The file is ignored by Git. Never paste full status/keys into committed reports. The example intentionally contains invalid placeholders so accidental use fails visibly.

## Configuration choices

- Postgres 17; application Data API exposes only `public`.
- `auto_expose_new_tables = false`: migrations must explicitly grant required access as well as enabling RLS.
- Signup enabled, anonymous Auth sign-in disabled; email confirmation enabled, 12-character password minimum and secure password changes.
- Exact local callback/reset URLs; add only reviewed local paths when authentication implementation requires them.
- Auth mail is captured locally. No real SMTP provider is configured.
- Storage enabled; vector storage, analytics and Edge runtime disabled until a verified feature needs them. Auth, database, REST, Storage, Studio, email capture and Realtime remain available.
- `supabase/seed.sql` is intentionally empty at initialization. P3 supplies deterministic domain seeds and API-based Auth/Storage provisioning.

## Migration workflow (P3 onward)

Use CLI help for flags supported by the pinned version:

```sh
npx supabase migration new content_schema
# Edit the new SQL file, then replay only the disposable sdgc stack:
npm run db:reset
npm run db:lint
npm run db:test
npm run db:types
```

`db:reset` deletes this project's local database contents and recreates them from migrations/seed. Check the working directory/project ID first. Never point this command at remote data or use a private WordPress export as test seed.

`npm run db:types` writes UTF-8 using a Node script to avoid PowerShell redirection encoding differences. The bootstrap contains types generated from the empty local application schema, and both clients already use its `Database` generic. P3 regenerates those types after implementing migrations; do not handwrite a pretend application schema.

P3 also adds `npm run db:provision` and `npm run test:integration`; they are not available in the bootstrap. They must reject hosted database URLs and use synthetic identities. Reset/reprovision twice to prove reproducibility.

## Verification and stopping

```sh
npm run check
npm run build
npx playwright install chromium
npm run test:e2e
npm run db:stop
```

The browser suite builds/starts the app automatically when no server exists. CI builds once before Playwright. Starting a dev server yourself can speed iterative checks, but delivery evidence must include the production build.

`db:stop` stops this repository's stack and preserves local data. Do not use destructive volume cleanup as a routine troubleshooting step.

## Environment troubleshooting

During initialization, Codex's restricted command launcher failed before executing commands because it enumerated a locked unrelated `I:` BitLocker volume. The approved alternate execution mode worked. That is a host launcher problem, not a Next.js or Supabase error. If it recurs in Antigravity, verify normal terminal execution first and record the environment issue accurately; do not change application code to mask it.

See `BOOTSTRAP-STATUS.md` for actual initialization results. Do not infer success from this runbook alone.
